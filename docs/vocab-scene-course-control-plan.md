# Контрольный план: слова ↔ сцена/дебат ↔ прогресс

Образовательный контур Speakeasy: **Словарь** (что учу) · **Практика** (где применяю) · **Прогресс** (как усваиваю).

Сессия практики слов: жёсткий лимит **≤5**. Полный список живёт в словаре и может быть длиннее.  
Контур один для **системных** и **личных** сценариев/дебатов.

---

## Принципы (не нарушать)

1. Список и сессия — разные сущности; список **всегда сохраняется** у пользователя.
2. Плохой fit сцена↔слова не маскируется промптом: фильтр / генерация / свои слова / старт без практики слов.
3. Прогресс — не отдельная вселенная, а витрина тех же событий (list / session / sense / scenario|debate).
4. Метрики — учебные (усвоение, перенос в речь, динамика), не vanity (сырые клики).
5. Можно: свой список, свои слова, AI‑список, переген **списка** или только **пятёрки сессии**.

---

## Три раздела продукта

| Раздел | Роль | Главный вопрос пользователя |
|--------|------|-----------------------------|
| Словарь | Учебные наборы + привязка к сценам | Что я учу? |
| Практика | Gate + диалог/дебат + ≤5 | Где я это применяю? |
| Прогресс | Сессия / список / слово / курс | Как это усваивается? |

## Механика метрик (образовательная платформа → наши особенности)

### Слои учёта (как в edtech, адаптировано)

| Слой edtech | У нас | Что меряем |
|-------------|--------|------------|
| Курс / модуль | Список, привязанный к сценарию или дебату | Покрытие списка, mastery списка, число прогонов |
| Урок / занятие | Одна практика‑сессия (диалог или дебат + ≤5 слов) | Исход пятёрки, подсказки, финал сцены |
| Учебная единица | Sense (значение слова) | SRS recognition/production, история в сессиях |
| Активность | Реплика / подсказка / assess | used / hinted / missed, production quality |
| Перенос (transfer) | Слово сказано в живой сцене, не только в карточках | «В речи» vs «только SRS» |

### События, которые обязаны писаться (event log под прогресс)

Каждая практика‑сессия со словами фиксирует минимум:

- `list_id`, `dialogue_session_id`, `agent_session_id`
- режим: `chat` | `roleplay` | `debate`
- привязка: `scenario_id` / personal scenario / debate topic key
- `sense_ids[≤5]` + причина отбора (fit / due / manual) — с этапа 3
- по каждому sense к концу сессии: `used` | `hinted` | `missed` (+ assess verdict, interval)
- исход оболочки: goalReached / debateCompleted / early exit
- источник списка сессии: `user` | `system` | `ai` | `mixed`

Без этого прогресс «потом» не восстановить.

### Метрики продукта (что показывать человеку)

**По сессии (урок)**  
- 5 слов: сказал сам / с подсказкой / не сказал  
- Краткий итог assess (усвоение в этой сессии)  
- Сцена/дебат + список‑источник  
- Дошёл ли до финала оболочки  

**По списку (модуль)**  
- Покрытие: % слов списка, хотя бы раз бывших в сессии  
- Воронка SRS списка: new → learning → due → mastered (recognition + отдельно production, если есть)  
- Тренд 7/30 дней: due↓, mastered↑, доля сессий без подсказки↑  
- Слабые слова: часто hinted/missed или провал production  
- Число сессий по списку; последняя активность  

**По слову (единица)**  
- История появлений across сессий  
- Улучшение/регресс (missed → hinted → used; SRS interval)  
- В каких сценах/дебатах встречалось  
- CTA: повторить в той же сцене / другая пятёрка / карточки SRS  

**Курсный слой**  
- Лента недавних сессий со словами  
- «Продолжить модуль»: тот же список + та же/следующая сцена  
- Простые цели‑вехи (см. ниже)  

### Вехи «полного курса» (mastery criteria)

Не один зелёный тик. Уровни, близкие к speaking‑progress по сценам:

1. **Exposed** — слово попало в сессию  
2. **Produced** — сказал в диалоге без подсказки (или assess ok)  
3. **Stable** — SRS interval / repetitions выше порога (у нас SM‑2)  
4. **Transferred** — produced в привязанной сцене/дебате ≥ N раз или в разных сессиях  
5. **Module clear** (список): доля слов на Stable/Transferred ≥ порога + due под контролем  

Для сценария/дебата как оболочки (уже есть speaking assessment) — **не заменять**, а **дополнять** слоем vocab: «сцена пройдена» ≠ «слова списка усвоены».

### Метрики для нас (продукт/качество контура) — не обязательно в UI

- Доля сессий с fit ≥ порога  
- % AI‑списков, не удалённых за 7 дней  
- Частота перегена сессии vs перегена списка  
- Доходимость до финала **со** словами vs без  
- Доля личных сценариев/дебатов с привязанным списком

## Этап 1 — Каркас стыковки + запись прогресса

**Ценность:** честный fit, свои слова, и уже пишутся факты для образовательной витрины.

### Словарь
- [x] Привязка списка к системному/личному сценарию или дебату (`source`: user/system/ai) — миграция + API create/patch/filter
- [x] Теги темы на списках (`theme_keys`) + автовывод при create/bind; сцена/дебат — через binding/context
- [x] Бейдж привязки в словаре + кнопка «Практиковать» (deep link в агент)
- [x] Свой список «под эту сцену/дебат» из gate (создать + секция «уже к этой сцене»)
- [x] Идемпотентность: create с binding reuse_bound → существующий список

### Практика
- [x] Gate: создать список под модуль | выбрать привязанный/подходящий | без слов
- [x] Мягкий фильтр fit (ранжирование + bound-секция + theme_keys)
- [x] Сессия = ≤5 + `list_id` в `vocab_dialogue_sessions`
- [x] Deep link словарь→практика; автопривязка списка после выбора сцены

### Прогресс (обязателен с этапа 1)
- [x] Persist `list_id` на сессии практики + API `/dialogue/recent`
- [x] used/hinted/missed в карточке (цветные чипы + сводка)
- [x] Секция «Слова в практике» в Progress (EN/ZH)
- [x] Не смешивать mastery сцены и слов — отдельный блок

**Готово, когда:** сцена/дебат (системный и личный) со своим списком; список в словаре с привязкой; после сессии в прогрессе видно, что было с пятёркой слов.

## Этап 2 — ИИ‑список, перегены, отражение в прогрессе

**Ценность:** идеальный fit по запросу; список — актив пользователя; пересборка под контролем.

### Словарь / Практика
- [x] Генерация полного списка (~8–20) под theme_profile сцены/дебата (`POST .../generate-for-context`)
- [x] Сохранение AI‑списка с привязкой; уровень CEFR/HSK; дебаты ≠ бытовой оффтоп
- [x] Переген **всего списка** (`POST .../:id/regenerate` mode=replace|new)
- [x] Переген **только сессии ≤5** (`POST .../:id/session-picks`, due→learning→new)
- [x] Предлагать существующий привязанный список вместо молчаливого клона (reuse)

### Прогресс
- [x] В истории: AI‑бейдж на модуле + recent уроки; переген сессии не создаёт ложный провал
- [x] Динамика модуля: покрытие / воронка / 7·30 / цели / module_clear
- [x] Не считать переген сессии как новый «провал» модуля — session-picks не создаёт сессию

**Готово, когда:** нет своих слов → собрать AI‑список → он в словаре → пятёрка в сессии → в прогрессе виден источник и перегены.

## Этап 3 — Умный топ‑5 + динамика усвоения

**Ценность:** в урок попадают нужные сейчас слова; прогресс показывает *почему* и *как сдвинулось*.

### Практика
- [x] Скоринг ≤5: fit к шагу + SRS (due → learning → new) + разнообразие (`vocab-session-picks` + session-picks)
- [x] Одна строка «почему эти» в gate (`reason` / `whyLine`)
- [x] Согласованность с practice_scene / фокусом в промпте (theme_text → fit; orderPracticeTargetsForScene в репликах)

### Прогресс
- [x] Динамика **по списку**: воронка SRS + тренд 7/30 + слабые слова (`GET .../course-modules`)
- [x] Динамика **по сессии**: итог assess в recent (сказал / подсказка / мимо) + CTA
- [x] Динамика **по слову**: timeline сессий + SRS (`GET .../senses/:id/course` + WordDetailCard)
- [x] Вехи Exposed → Produced → Stable → Transferred (бейджи на слабых словах модуля)
- [x] CTA из прогресса: продолжить модуль / другая пятёрка / SRS due списка

**Готово, когда:** пользователь видит усвоение на трёх зумах (сессия / список / слово) и может продолжить курс одним действием.

## Этап 4 — Полный образовательный курс (полировка)

**Ценность:** привычный контур «модуль → урок → отзыв → следующий шаг».

### UX курса
- [x] Единый gate и навигация словарь ↔ практика ↔ прогресс (`VocabCoursePillars` + deep links / repick)
- [x] Лента занятий со словами; цели‑вехи модуля («закрыть due», «3 сессии без подсказки»)
- [x] Speaking progress сцены и vocab progress списка на одном экране прогресса, но разными блоками (hero speaking + модули слов)
- [x] Правила порога fit зафиксированы в копирайте и поведении (`SCENE_FIT_FLOOR`, gate copy)

### Метрики качества контура (внутр.)
- [ ] Дашборд/логи по product‑метрикам — **не делаем** (ops-админка лишняя на этом этапе)
- [x] Проверка: личный сценарий даёт тот же учебный цикл, что системный (тот же binding/gate/progress)

### Инварианты
- [x] Лимит 5 на сессию; выход/финал не удаляет список
- [x] Смена режима только после выхода/финала (как сейчас)
- [x] Карточный SRS и практика в диалоге кормят **одни** sense‑состояния (`last_move_source` в course слова)

**Готово, когда:** новый пользователь за один проход отвечает на «что / где / как усваиваю» и понимает следующий шаг курса.

---

## Сознательно не делаем

- Переписывать все системные сюжеты под произвольные списки  
- Держать AI‑пятёрку без сохранённого полного списка в словаре  
- Склеивать любой список с любой темой одним промптом  
- Подменять прогресс сцены прогрессом слов (или наоборот)  
- Vanity‑метрики вместо усвоения и переноса в речь  
- Учительский / родительский / школьный кабинет (мультиаккаунт, отчёты для педагога) — **out of scope** v1–v4, пока нет отдельного продукта

## Добивки и риски (зафиксировано)

Ядро плана достаточное для v1 курса. Ниже — дыры, которые иначе всплывут в середине разработки. Каждой назначен этап или out of scope.

### D1. Единая правда SRS: карточки ↔ диалог
- **Суть:** recognition/production SM‑2 и практика в сессии должны кормить **одни** `vocab_srs_states` / assess. Явно: что считать «повторил» — только карточка, только сессия, или оба с разными весами.  
- **Зачем:** иначе прогресс по списку врёт (due в карточках, «усвоено» в чате или наоборот).  
- **Куда:** правила — этап 1 (события + assess уже пишет production); витрина согласованности — этап 3–4.  
- [x] Зафиксировать матрицу: recognition ← карточки; production ← assess диалога; статусы сессии used/hinted/missed — витрина  
- [x] В прогрессе слова показывать источник последнего сдвига (карточка / сессия)

### D2. Конфликты привязки и удаления
- **Суть:** один список на несколько сцен vs копия «под сцену»; удалили личный сценарий / список / AI‑клон — что с прогрессом и сессиями.  
- **Зачем:** не потерять историю усвоения и не оставить битые бейджи.  
- **Куда:** этап 1 (модель связи many‑to‑many или primary + secondary); этап 4 (мягкое удаление / «сцена удалена, список оставлен»).  
- [x] Правило v1: **одна primary‑привязка + theme_keys** (без обязательной копии на каждую сцену)  
- [ ] При удалении сцены: список и sense остаются; в прогрессе — «сцена недоступна» — soft later  
- [ ] При удалении списка: сессии в истории read‑only — soft later

### D3. Свободный чат в том же курсе
- **Суть:** freestyle без сценария — модуль «тема чата» / список без scene_id или с `mode=chat`.  
- **Зачем:** иначе чат со словами выпадает из прогресса курса.  
- **Куда:** этап 1 (те же события с `mode=chat`); этап 4 (как показывать модуль без сцены).  
- [x] Сессии chat пишутся в тот же event log (`vocab_dialogue_sessions.mode=chat`)  
- [x] В прогрессе: бейдж «Свободный диалог» на модуле + recent

### D4. ZH vs EN — один контур, разные поверхности
- **Суть:** дебаты в основном EN; ZH — сценарии/чат, другие уровни (HSK). Теги, генерация, прогресс не должны разъехаться.  
- **Зачем:** два «полупродукта» сломают ощущение курса.  
- **Куда:** этап 1 (теги/привязки language‑aware); этап 2 (генерация с HSK/CEFR); этап 4 (проверки паритета UX без дебатов в ZH).  
- [x] Все сущности списков/сессий несут `language`  
- [x] Прогресс фильтруется по языку обучения, как сейчас speaking progress  
- [x] AI‑список для ZH не опирается на debate‑only ветки (force roleplay / 400 в UI)

### D5. Лимиты и стоимость AI
- **Суть:** генерация списка и перегены — LLM; нужны квота / баланс / потолок перегенов на сцену.  
- **Зачем:** не сжечь бюджет и не дать бесконечный «ещё раз» без трения.  
- **Куда:** этап 2 (продуктовые лимиты + биллинг как у других agent‑операций).  
- [x] Переген сессии (без LLM) vs переген/генерация списка (LLM, billable с баланса пользователя)  
- [x] UX при 402: явное «пополните баланс»; превью до persist; «сгенерировать снова» = ещё списание

### D6. Fit vs SRS (педагогический антипаттерн)
- **Суть:** due‑слово, которое ломает сцену, не должно побеждать fit «ради SM‑2».  
- **Зачем:** иначе снова натяжка и плохой перенос в речь.  
- **Куда:** этап 3 (порядок скоринга: **сначала fit‑порог, внутри — SRS**); этап 4 (копирайт).  
- [x] Слова ниже fit‑порога не попадают в пятёрку, даже если due (`SCENE_FIT_FLOOR`)  
- [x] Due без fit → карточки SRS или другая сцена, не насильственный диалог (reason + gate copy)

### D7. Приватность и глубина истории
- **Суть:** для «слово в сессии» нужны цитаты/реплики или достаточно агрегатов used/hinted/missed?  
- **Зачем:** GDPR‑ожидания, объём хранения, достаточно ли для timeline.  
- **Куда:** этап 1 (минимум: агрегаты + sense_id + session_id); опционально quote — этап 4.  
- [x] v1: без хранения полных реплик в vocab‑progress, только статусы/verdict (sense course timeline)  
- [x] Quote opt‑in / TTL — не делаем в v1

### D8. Онбординг «что / где / как»
- **Суть:** первый заход: за 30 секунд объяснить три раздела курса.  
- **Зачем:** иначе мощный контур выглядит как три разрозненных экрана.  
- **Куда:** этап 4 (можно тонкий hint на этапе 1 у gate).  
- [x] Один короткий coach‑mark или пустое состояние gate + прогресса (`VocabCoursePillars`)  
- [x] Не модал‑роман: максимум один экран

### D9. Качество AI‑списка до сохранения
- **Суть:** фильтр мусора, дублей, off‑level, off‑topic **до** записи в словарь; переген — запасной путь, не единственный.  
- **Зачем:** меньше мусора в словаре и в прогрессе модуля с нуля.  
- **Куда:** этап 2.  
- [x] Валидация: язык headword, русский gloss, дедуп, placeholder junk, мин. доля темы (`validateBoundListDraft`)  
- [x] Превью списка → подтверждение пользователя → persist (generate/regenerate); retry QC при браке

### D10. Учитель / родитель
- **Суть:** отчёты для третьих лиц, классы, назначения.  
- **Статус:** **out of scope** до отдельного продукта.  
- [ ] Не закладывать роли teacher/parent в схему этапа 1–4  
- [ ] События пользователя достаточно богаты, чтобы позже построить teacher‑view без миграции с нуля (list/session/sense уже есть)
