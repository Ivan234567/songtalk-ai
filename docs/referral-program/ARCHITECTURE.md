# Архитектура реферальной программы

Проект поверх текущего Supabase и `backend/src`. Новая платёжная система не заводится: баланс ученика остаётся `user_balances`, списание остаётся `deduct_balance` и `settle_operation`.

Схема этапа 2 зафиксирована в `supabase/migrations/20261112180000_referral_program.sql`. Ниже по тексту местами ещё лежит ранний набросок с отдельными кампаниями и cookie. Для таблиц, ссылки `/r/{code}` и денег источником правды является миграция: код партнёра лежит в `partners.referral_code`, кампания — поле перехода, cookie нет.

## Как устроен вход сейчас

```text
регистрация email  frontend/app/auth/register/page.tsx
                   supabase.auth.signUp, без кода партнёра

регистрация Яндекс backend/src/yandex-auth.js
                   supabase.auth.admin.createUser

первый запрос     POST /api/auth/exchange-supabase-token
                   backend JWT, и сейчас же бонус 50 ₽
```

Дальше `resolveUserId` принимает backend JWT или Supabase access token. Платные вызовы идут с этим идентификатором. Реферальную привязку нужно ставить на сервере в момент, когда пользователь уже известен, а не верить телу запроса с клиента.

Естественная точка — тот же обмен токена: через него проходят и email, и Яндекс. До обмена код кампании живёт в браузере так же, как уже живёт сессия: в `localStorage`, не в cookie. После обмена атрибуция записывается один раз.

Своих cookie проект не ставит. Backend JWT пишется в `localStorage` ключом `backend_jwt` (`frontend/lib/backend-jwt.ts`, комментарий в `frontend/app/auth/callback/page.tsx`). Клиент Supabase в `frontend/lib/supabase.ts` тоже хранит сессию в хранилище браузера. Упоминание cookie в `frontend/app/legal/privacy/page.tsx` не подкреплено кодом установки cookie.

## Ссылка и переход

Публичная страница, без кабинета:

`frontend/app/r/[code]/page.tsx`.

Страница один раз вызывает `POST /api/referrals/click` с кодом. Сервер проверяет, что кампания активна и партнёр не выключен, и пишет переход. Страница кладёт в `localStorage` код и время перехода, затем ведёт на `/auth/register?ref={code}`.

Регистрация по email передаёт этот код в `supabase.auth.signUp` как `options.data.referral_code`. Так код переживает письмо подтверждения: он оказывается в `user_metadata`, а не только в адресе. Яндекс-вход передаёт тот же код на уже существующий серверный маршрут создания пользователя. Обмен токена читает код из `user_metadata`. Тело запроса с клиента может продублировать код, но сервер сверяет его с кампанией и не верит ему в обход metadata, если metadata уже есть.

В переход не пишутся email, имя и IP. Повторное открытие той же ссылки в том же браузере не плодит клики: страница помнит последний удачный код в `localStorage`. Новый код заменяет предыдущий по правилу, которое выбрано ниже. После регистрации новые переходы увеличивают счётчик кликов, но атрибуцию не меняют.

## Таблицы

Имена новые. Существующие `user_balances`, `balance_transactions`, `balance_operations`, `payment_orders`, `user_profiles` не подменяются.

### partners

Партнёр — обычный пользователь `auth.users`.

| Поле | Смысл |
|---|---|
| id | uuid |
| user_id | уникальная ссылка на `auth.users` |
| status | `active` или `disabled` |
| display_name | имя в кабинете |
| payout_note | короткая пометка администратора, не реквизиты, пока реквизиты не подтверждены |
| created_at, updated_at | |

Отдельного пароля нет. Вход тот же, что у ученика. Маршрут `/partner` пускает только строку со `status = active`.

### partner_campaigns

| code | уникальный код ссылки |

Ссылка: `{origin}/r/{code}`.

### referral_clicks

| Поле | Смысл |
|---|---|
| id | uuid |
| campaign_id | |

Партнёр видит число строк за период, не список переходов.

### referral_attributions

Один пользователь — одна строка. Уникальный `user_id`.

| Поле | Смысл |
|---|---|
| user_id | кто зарегистрировался |
| partner_id | кому засчитано |
| campaign_id | код из `user_metadata` на момент привязки |
| click_id | переход, если ещё находится |
| created_at | |

Повторный обмен токена видит строку и ничего не меняет. Самореферал: `partners.user_id` совпал с новым `user_id`, либо email партнёра совпал с email нового пользователя. Строка атрибуции тогда не создаётся.

### welcome_bonus_grants

Уникальный `user_id`. Сумма 50 ₽. Ссылка на транзакцию баланса. Это закрывает гонку в `exchange-supabase-token`: вставка гранта и зачисление баланса делаются одной функцией, повтор возвращает `already`.

Пока не решено, давать ли 50 ₽ всем или только привлечённым. Таблица одинаково запрещает второй грант в обоих вариантах.

### bonus_lots и paid_balance_rub

Сейчас бонус и оплата неразличимы. Добавляется учёт, не второй кошелёк в интерфейсе ученика.

`user_balances` получает `paid_balance_rub`. Инвариант: `balance_rub = paid_balance_rub + сумма остатков bonus_lots`. Ученик по-прежнему видит одно число через `GET /api/balance`.

`bonus_lots`: источник (`welcome` или `adjustment`), исходная сумма, остаток, `user_id`.

При списании функция атомарно уменьшает сначала одну часть, потом другую. Какая часть первая — открытое решение. В `usage_economics` пишется, сколько снято с бонуса и сколько с оплаченного остатка.

Существующие балансы при миграции целиком помечаются как оплаченные, кроме транзакций `topup_manual` с `metadata.reason = welcome_bonus`, если остаток это ещё позволяет. Если баланс уже потрачен ниже бонуса, остаток бонуса становится нулём, история назад не переписывается. Это единственная догадка о прошлом, и она не порождает партнёрских начислений.

### usage_economics

Неизменяемый журнал. Одна строка на `operation_id`.

| Поле | Смысл |
|---|---|
| operation_id | тот же, что у списания |
| user_id | для расчёта на сервере, партнёру не отдаётся |
| partner_id | снимок атрибуции, может быть пустым |
| service | `deepseek-v3.2`, `whisper-1`, `gpt-4o-mini-tts` |
| charge_rub | сколько сняли с ученика |
| bonus_charge_rub | часть из бонуса |
| paid_charge_rub | часть из оплаченного остатка, это учитываемая выручка |
| provider_cost_rub | факт или запас |
| provider_cost_source | `aitunnel` или `fallback` |
| tax_rub | пусто, пока нет правила налога |
| net_profit_rub | пусто, пока пуст налог |
| created_at | |

`UPDATE` обычным ролям не выдаётся. Исправление — новая строка `usage_adjustments` со ссылкой на исходную, знаком суммы, основанием и `author_user_id`.

### partner_ledger

Неизменяемый. Уникальный ключ идемпотентности.

Типы: `accrual`, `hold`, `release`, `payout`, `adjustment`.

`accrual` ссылается на `usage_economics` или на пачку за период и не содержит email ученика. Основание для кабинета: период, услуга, число операций, суммы. Имена учеников не попадают в `basis`.

Доступная сумма не хранится отдельным балансом, который можно разъехать. Она считается из журнала: начисления, которые уже `release`, минус выплаты и корректировки. Черновик до выбора налога помечается `hold` и в доступную сумму не входит.

### partner_payouts

Администратор фиксирует выплату. Поля: партнёр, сумма, момент, `author_user_id`, комментарий, ссылка на строку `partner_ledger` типа `payout`. Статуса платёжной системы нет: запись означает «выплата учтена», а не «банк подтвердил».

### admin_users

`user_id` первичный ключ на `auth.users`. Строки заводятся миграцией или ручным SQL, не из публичной формы. Проверка на каждом админском запросе. Общего секрета `ADMIN_BALANCE_SECRET` для новой панели недостаточно: секрет не говорит, какой человек нажал кнопку, а журнал корректировок обязан хранить автора.

## API

Все маршруты ниже проверяют пользователя на сервере. Суммы с клиента не принимаются, кроме явной суммы выплаты, и та не может превысить доступный остаток журнала.

Партнёр, только свои данные:

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/partner/summary` | переходы, регистрации, активные, платящие, выручка, расход, прибыль, 40%, доступно, выплачено |
| GET | `/api/partner/campaigns` | название, код, ссылка, своя статистика |
| POST | `/api/partner/campaigns` | имя кампании, код генерирует сервер |
| GET | `/api/partner/ledger` | период, тип, сумма, основание без персональных данных |
| GET | `/api/partner/payouts` | дата и сумма |
| GET | `/api/partner/me` | имя и статус |
| POST | `/api/auth/logout` | не нужен: выход уже на клиенте через Supabase |

Активный пользователь в сводке — тот, у кого есть хотя бы одно списание `usage` за выбранный период. Платящий — у кого есть `topup_gateway` или `topup_manual` без `reason = welcome_bonus`. Оба числа считаются на сервере, список людей не возвращается.

Администратор:

| Метод | Путь |
|---|---|
| GET | `/api/admin/partners/summary` |
| POST | `/api/admin/partners` |
| PATCH | `/api/admin/partners/:id` |
| GET | `/api/admin/partners/:id` |
| POST | `/api/admin/partners/:id/payouts` |
| POST | `/api/admin/partners/:id/adjustments` |

Создание партнёра: администратор указывает email уже существующего пользователя. `get_user_id_by_email` можно вызвать только с сервера. Новая публичная регистрация «я партнёр» не открывается.

Публично без сессии доступен только переход `/r/[code]`.

## Где писать экономику

В `settle_operation` и в успешном `deduct_balance` после списания вызывается одна функция `record_usage_economics`. Она:

1. Делит списание на бонус и оплаченный остаток.
2. Берёт `provider_cost_rub` из аргумента.
3. Если аргумент пустой, ставит запас из `balance-rates.js` и `source = fallback`.
4. Находит атрибуцию. Нет атрибуции — строка экономики всё равно пишется, `partner_id` пустой, начисления партнёру нет.
5. Повтор того же `operation_id` не создаёт вторую строку.

Чтобы факт закупки попадал в аргумент:

- озвучка уже передаёт `cost-rub`
- текст: читать `usage.cost_rub` из ответа AITunnel в `runBillableChat` и передавать как `providerCostRub`, списание с ученика по-прежнему считает `getCost`
- распознавание: запросить у AITunnel формат с `usage.cost_rub` в `backend/src/stt.js` и передать его так же

Списание с ученика из-за этого не меняется. Меняется только то, какой расход ляжет в журнал партнёра.

## Атрибуция: варианты, не решение

Срок и выбор между несколькими переходами не зафиксированы.

1. Последний переход, код в `localStorage` живёт 30 дней. Регистрация закрепляет код из `user_metadata`. Ближе к обычной рекламной ссылке.
2. Первый переход, 30 дней. Поздний партнёр не перехватывает человека, который уже открыл ссылку раньше.
3. Последний переход, 7 дней. Короче окно, меньше споров о старых ссылках.
4. Только до закрытия вкладки, через `sessionStorage`. Почти не переживает подтверждение почты.
5. Без срока до регистрации, последний код побеждает. Просто, но старая ссылка живёт сколько угодно.

Общее для всех вариантов, это уже требование, а не выбор: после строки в `referral_attributions` партнёр не меняется; повторные клики считаются; самореферал не создаёт атрибуцию; бонус не начисляется второй раз.

## Интерфейс

`/partner` — отдельное приложение внутри того же Next.js, не вкладка `dashboard`. Ученик без строки партнёра получает отказ, а не чужую статистику.

Визуально те же переменные из `frontend/app/globals.css` и шрифт Onest из `frontend/app/layout.tsx`. Карточки сумм крупнее таблиц. Таблица появляется в истории начислений и выплат, не на первом экране. На ширине телефона карточки в один столбец. Графики первого этапа — полосы на CSS, без новой зависимости.

Админка не ссылается из кабинета ученика и не лежит в `Sidebar.tsx`. Прямой адрес без строки в `admin_users` отвечает 404, чтобы не подтверждать существование панели.

Реквизитов в форме партнёра нет, пока не выбрано хранить ли их. В настройках: имя, статус, основная ссылка, выход.

## Что сознательно не делаем в первой схеме

- Не показываем партнёру людей.
- Не платим партнёру через ЮKassa.
- Не пересчитываем старые списания в 40%.
- Не считаем пополнение выручкой.
- Не подставляем цену «от 41,76» вместо `cost-rub`.
